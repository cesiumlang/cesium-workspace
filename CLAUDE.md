# Cesium Workspace

This repository is the parent of the Cesium repositories. It has no code of its own; its `.claude/` holds the agent setup (skills, rules, subagents). Its submodules, side by side:

- `cesium-src/` is cesiumlang/cesium, the compiler. Its submodules: `buildtools/` (cesium-buildtools), `.cspell/cesium/` (cspell-cesium).
- `cesiumlang.org/` is the website, built with Zine from Markdown (`zig build`). Its submodules: `grammar/`, `.cspell/cesium/`.
- `devkits/` builds the devkit. Its submodules: `qbe/`, `llvm-project/`.
- `vscode-cesium/` is the VS Code extension and the temporary language server `zcsls` (Zig). Its submodule: `grammar/`.
- `dot-github/` is cesiumlang/.github, the organization profile and the shared workflows.

## Rules

- Do not redirect output to NUL (`2>nul`, `> NUL`); it does not work as expected on Windows. Let commands print.
- Indentation is two spaces (Zig: four, as `zig fmt` writes). Language-specific rules are in `.claude/rules/` and load with the files they cover.
- Builds use the Zig of the Cesium devkit (`cesium-src/.devkit`, `bash tools/fetch-devkit.sh`), not the VS Code extension's Zig.
- Other external tools come from `cesium-src/buildtools` (`buildtools.bat`), so a developer needs nothing preinstalled: the Vulkan SDK, Node.js, the tree-sitter CLI, direnv, Qt. Code uses those copies (the buildtools Vulkan SDK, never a system-wide one, which is left alone). A new tool is added there as a pinned, checked download.
- The `.envrc` files are the one source of the environment, loaded by direnv (from buildtools) for every consumer: Git Bash (`cesium-src/buildtools/direnv-hook.sh` sourced in `~/.bashrc`), VS Code (started from such a shell; the direnv extension is not used, as the buildtools readme explains), and Claude Code sessions (the `SessionStart` hook `.claude/hooks/direnv-env.sh`). Node.js comes from buildtools, and from fnm only where buildtools has none.
- No Python in any Cesium repository, as it cannot be assumed installed: scripts are bash or batch files; programs that are part of the build or the tests are Zig (cesiumlang/cesium#90).
- Disk space is limited: no large downloads in the background (a test VS Code, toolchains, archives; CI does those); few Git worktrees, inside `C:\cesium`, removed when done; delete branches once merged, keeping only `main` and `dev`.

## How work is done here

- The design is decided through proposals, by emanspeaks (`cesium-src/proposals/0000-documentation-system.md`; the `cesium-spec` skill has the how). The charter (`cesium-src/docs/charter.md`) and the proposals (`cesium-src/proposals/`) decide; the specification (`cesium-src/spec/`) records, rule by rule, with each rule's source; issues track the work and the open questions (`design`, `audit`; the former `decision` issues #4 to #11 track the proposals P-0002 to P-0009). Before deciding anything about the language or the compiler, find the rule, proposal or issue that decides it and cite it. List anything decided without such guidance under "Choices made without guidance" in the pull request. Never close or decide an open design question, and never set a proposal `accepted`.
- Writing or reading Cesium code: the `cesium-language` skill says where the decided syntax is and how to check code with the compilers.
- Whatever needs a design decision or emanspeaks's input: label the issue `question` (`design` in cesiumlang/cesium), assign emanspeaks, leave it open. Recommend an answer only where one is unambiguous or obvious.
- The repository owner is `emanspeaks` in every file, issue, pull request and comment: never his first name (copyright lines and `package.json` authors excepted). Write `emanspeaks` without `@` when recording a direction he gave; `@emanspeaks` only where his input or attention is needed, since every `@` notifies him. Mind that `RandyOS` and `randyos-*` are project and app names.
- Whose action is next is said three ways, kept the same (emanspeaks, 2026-11-21): emanspeaks is the assignee only where he must answer or do something Claude cannot; everything else is the agent's, with no assignee, the label `agent`, and "Next action: agent" in the Roadmap project. When the next step changes hands, change all three (`next-action.sh` in the `roadmap-project` skill does it for the whole project). The machine account `emanspeaks-bot`, which used to be the assignee of Claude's work, cannot be assigned since GitHub flagged it.
- The GitHub Project [Cesium Roadmap](https://github.com/orgs/cesiumlang/projects/1) is the source of truth for the order of all work. Every new issue goes into it at its place in the priority order, and every plan is an issue, however far off (no draft items); the `roadmap-project` skill has the procedure and scripts.
- On GitHub, Claude acts as the GitHub App Cesium Agent, never as emanspeaks, and commits as its bot; the `github-as-cesium-agent` skill has the commands, the `emanspeaks-bot` fallback and its limits. Never print, copy or commit anything in `C:\scratch\github-apps\cesiumlang\`.
- Every repository has `main` and `dev`. Work goes to `dev` through pull requests; `dev` goes to `main` through the standing pull request from `dev` to `main` that each repository with CI keeps open. Nothing blocks `dev` (emanspeaks, 2026-11-21; as zfls and rstd): no check is required there and CI does not start for it, so a merge into `dev` never waits; CI runs on the standing pull request, which each merge into `dev` restarts, on pushes to `main`, and by hand (`gh workflow run <workflow> --ref BRANCH`). Once a repository has a tagged release (devkits; check its tags), emanspeaks reviews and merges its `dev` to `main` pull request.
- A repository that states its version in more than one file keeps `.github/workflows/version.sh` (vscode-cesium; as chasingdaylight/skein): it lists every such place, CI checks them on every run and sets them all when it begins the next version (`version.sh set NEXT`). A new place that states the version goes into it (emanspeaks, 2026-11-26).
- Each submodule here records the `dev` head of its repository: after a merge to a submodule's `dev`, move the pointer here in the same piece of work.
- emanspeaks's uncommitted edits to `CLAUDE.md`, the LTeX dictionary and false-positive files, and readmes, in any repository here, go into the next commit there. He says when he is writing something larger to leave alone.
- A setting or tool requirement added to a submodule's `*.code-workspace` or `.envrc` is repeated in `cesium-workspace.code-workspace` and `.envrc` here. LTeX reads only this root's dictionary, so words added to a submodule's `.vscode/ltex.dictionary.en-US.txt` go into the one here too.
- The website takes the specification and the proposals from a checkout of the compiler, rendered by Skein (`tools/take-spec.sh`; cesiumlang/cesium#106), but does not build it: its CI installs the Zig version that is set by hand as `ZIG_VERSION` in `cesiumlang.org/.github/workflows/deploy.yml` and in `.github/workflows/pages.yml` of cesiumlang/cesiumlang.dev (the dev site) and of emanspeaks/cesium-site-mirror (the mirror at cesium.randyeckman.com, which repeats the build steps of `deploy.yml`; emanspeaks's own repository, so changed with plain `gh` and `git`, not as the app), and locally it uses the devkit's Zig. **When the devkit's Zig version changes, change it in every place that pins one**: those three workflows, `minimum_zig_version` in the `build.zig.zon` files here, the devkit's own version file, and any other workflow or file that names a Zig version (search the repositories for the old version).
